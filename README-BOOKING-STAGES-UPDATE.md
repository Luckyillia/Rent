# Обновление: заявка на бронь + антиспам + пересмотр стейджей

Этот пакет кладётся поверх файлов из первого архива
(`forward-auto-rent-supabase-update.zip`) — заменяет часть файлов и
добавляет новые.

## Что изменилось

### 1. Бронирование — теперь отдельная страница-заявка

- Кнопка «Забронировать» на странице машины (`/car/:id`) ведёт на
  `/book/:id` вместо мгновенного создания брони.
- Форма на `/book/:id`: ссылка на ВК, игровое имя, «как обращаться»,
  срок (сутки/неделя). После отправки — «Заявка подана, будет
  рассмотрена в течение суток».
- Заявка больше НЕ создаётся напрямую из браузера через anon-ключ —
  теперь это отдельная Edge Function `create-rental`. Причина: чтобы
  антиспам по IP нельзя было обойти прямым вызовом Supabase REST API
  в обход сайта.

### 2. Антиспам

- `create-rental` проверяет: если с этого IP уже была заявка за
  последние **10 минут** — отклоняет с понятным сообщением.
- Порог задан константой `RATE_LIMIT_MINUTES` в самом начале файла
  `supabase/functions/create-rental/index.ts` — поменяйте на своё
  значение, если 10 минут не подходит.
- Важно: определение IP через заголовок `x-forwarded-for` — это
  стандартный, но не железобетонный способ (кто-то может сидеть за
  одним NAT/VPN с другими игроками, кто-то может менять IP). Для
  игрового сервера с адекватной аудиторией этого обычно достаточно;
  если понадобится более строгая защита (капча, лимит на ВК-ссылку
  и т.п.) — это отдельная доработка.

### 3. Стейджи — теперь с зависимостью и повторами

Как в итоге работает:

- **0 стейджей** — машина стоковая.
- **2–4 стейджа** — только подряд, без пропусков: нельзя поставить
  стейдж №2, если нет №1 (База); нельзя №3, если нет №2; и т.д.
- Слот 1 всегда — категория **База**.
- Слоты 2–4 — на выбор из **Баланс / Скорость / Управление**, причём
  **категории могут повторяться** (например, дважды «Скорость» на
  разных слотах одной машины).
- В админке (`/admin` → Машины) это теперь не чекбоксы, а выпадающий
  список «Количество стейджей» (Стоковая / 2 / 3 / 4) + по одному
  select-у на каждый слот, начиная со второго.
- Правило «0 или подряд 2–4, первый — база» проверяет сама
  Edge Function `admin-api` при сохранении (не сама БД) — если
  что-то не сходится, вернёт понятную ошибку вместо сохранения.

## Что нужно сделать у себя

### Шаг 1 — обновить базу

Если база уже создана по первому архиву — выполните в SQL Editor:

```
supabase/migration_booking_stages.sql
```

Если разворачиваете с нуля — просто выполните целиком новый
`supabase/schema.sql` из этого архива (он уже включает все изменения).

### Шаг 2 — задеплоить новую функцию и обновлённую admin-api

```bash
supabase functions deploy create-rental --no-verify-jwt
supabase functions deploy admin-api --no-verify-jwt
```

(`admin-login` не менялась, передеплоивать не нужно.)

### Шаг 3 — заменить файлы фронтенда

Скопируйте поверх текущих:

```
src/App.jsx
src/api/rentals.js
src/components/StagesList/StagesList.jsx
src/pages/VehiclePage/VehiclePage.jsx
src/pages/AdminPage/VehiclesAdmin.jsx
src/pages/AdminPage/RentalsAdmin.jsx
```

И добавьте новые:

```
src/pages/BookingPage/BookingPage.jsx
src/pages/BookingPage/BookingPage.css
```

Плюс добавьте содержимое `src/pages/AdminPage/AdminPage.append.css`
в конец существующего `src/pages/AdminPage/AdminPage.css` (новые
стили для выпадающих списков стейджей).

### Шаг 4 — перезапустить dev-сервер

```bash
npm run dev
```

## Если у вас уже были тестовые брони по старой схеме

Миграция удаляет старые колонки `renter_name` / `renter_contact` —
если там были нужные тестовые данные, сохраните их вручную перед
выполнением `migration_booking_stages.sql` (например, `select * from
rentals;` и скопировать).
